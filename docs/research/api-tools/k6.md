# Grafana k6 调研：让 Reva 接上性能测试，而不扩成压测平台

调研日期：2026-11-16。实际检索时间：2026-11-16T22:38:00+08:00（执行主机报告的时区）；Reva 起始基线由 `git rev-parse HEAD` 核实为 `72bf5de0d58bbc08e49b4ef0254b1f5eeec4c910`。规范仓库为 [grafana/k6](https://github.com/grafana/k6)，分类为 `performance`；检索时最新正式版为 **v2.4.0，2026-11-12 发布**。[1][5] 机器可读版本见 [k6.json](k6.json)。

**结论：k6 最值得 Reva 借鉴的是可重复执行、明确的失败门禁和稳定结果契约。** Reva 已经有脚本、GraphQL、WebSocket、OpenAPI 导入和可选加密同步；应补齐轻量本地回归路径，再把复杂负载交给 k6。当前没有必须阻断使用的 P0 建议，不建议为追求功能数量重造 VU 执行器、浏览器驱动或分布式压测。

## 1. 定位、架构和许可证

k6 是以代码表达场景的性能测试 CLI。Go 核心承担网络、执行器和指标；嵌入 Sobek 运行 JavaScript，TypeScript 经 esbuild 转译而非做类型检查。它不是 Node.js，不能假定所有 npm 包和 Node API 都可直接运行。生命周期分为 init、一次 setup、各 VU 的迭代函数、一次 teardown；场景控制执行函数、起始时间、环境和标签。实际执行及摘要路径可在 v2.4.0 的 `internal/js/runner.go`、`internal/cmd/run.go` 核对。[2][11][12][26][27][28]

本地 `k6 run` 不要求 Grafana 账户，脚本、数据和输出可留在本机，适合 Git 和 CI。远程模块导入、自动扩展解析和 Cloud 输出则有额外联网与数据流，不能把所有运行模式一概称为离线。[11][13][20][23]

| 层次 | 已核实边界 |
| --- | --- |
| 核心许可证 | README 写 `AGPL-3.0`，许可证文件是 GNU AGPL v3；GitHub 元数据也返回 `AGPL-3.0`。这是 OSI 批准的开源许可证，**不是仅源码可见的专有许可**。[1][2][3][4] |
| SPDX 精度 | `AGPL-3.0` 是旧的、已弃用 SPDX 标识，sidecar 保留实际返回值 [36][37]，并明确未独立消解 `-only` / `-or-later`；不能把 LICENSE 末尾“如何应用许可证”的示范段落当作每份源码的额外授权。 |
| 社区本地能力 | 场景执行、阈值、协议测试、脚本、指标、本地仪表盘和 HTML 报告均有核心/官方开源文档依据，不需要购买 Cloud。[6]–[20] |
| 商业服务 | Grafana Cloud 提供托管执行、在线 Test builder/Script editor、团队分析等服务，存在商业套餐与免费额度；免费额度不使服务代码自动成为 AGPL 核心的一部分，本文不承诺具体价格或额度。[23][24] |
| 独立项目与扩展 | README 链接的 k6 Studio 是独立录制/生成脚本桌面项目；Kubernetes 执行由独立 k6-operator 编排；扩展各有构建方式和许可证。本文没有把它们算作核心原生 UI 或统一许可证范围。[2][20][22][25] |

对 Reva 的实际含义是采用文件和进程边界做互操作，不复制或链接 k6 的 AGPL 实现代码，也不要求 Reva 用户建立云账户。扩展和分发方案仍应按实际使用的组件核查许可证，本文不是法律审计。

## 5. 给 Reva 的三个最小改进

### P1：有界的本地集合顺序回归

- **用户场景**：发布前对一个文件夹的十几个接口做重复冒烟验证，一次运行就能看出失败请求和断言。
- **现有缺口**：发送、取消、超时、认证、变量、pm.test 都已有；缺的是集合范围、冻结输入、运行状态和统一失败策略。
- **最小 PR**：新增不依赖 UI 的顺序执行服务，加一个 Viva 入口；冻结所选请求、实际继承认证和环境快照，HTTP/GraphQL 每次单并发执行一次，WS 明确跳过，限制请求数量与总时限。支持遇错停止、继续和取消；前置脚本错误视为运行失败。第一版不做跨请求变量回写或负载阶段。
- **依赖/范围**：复用 `RequestService`、`auth.Resolve`、`vars`、`script` 和集合树；无需新库。未来实施需协调集合入口、`app.go`、i18n 的文件所有权，本调研没有改它们。
- **验收**：`httptest` 记录三条请求顺序；第二条断言失败时，停止模式不发送第三条，继续模式保留失败并完成；取消正在等待的请求后不再发送。覆盖无认证屏障、环境覆盖、WS 跳过说明和脚本超时，确认集合/环境/原请求未被修改；GUI 用现有 headless harness 验证进度、结果与取消。

### P1：版本化运行报告与无窗口 CI 入口

- **用户场景**：小团队把原生集合放进 Git，CI 检测接口回归、阻止发布，并留下可解析结果。
- **现有缺口**：标签测试结果和历史不是稳定运行报告；现有仓库构建 CI 不能运行用户集合。k6 #4803 说明依赖终端文本的长期成本。
- **最小 PR**：以前一项纯 Go 服务为基础，增加独立 `cmd/reva-run`；读原生集合及可选环境，输出带 `schemaVersion`、时间、请求 ID、状态、耗时、断言、跳过原因的 JSON。规定成功 `0`、请求/断言失败 `1`、输入错误 `2`。报告默认省略 URL 查询、认证、正文和脚本日志，不回写数据目录；不用 GUI 启动流程承载 CLI。
- **依赖/范围**：依赖第一项执行服务；单独评审报告兼容约定与退出码。保持账户可选、文件作为输入输出，无需第三方依赖。
- **验收**：用临时目录与 `httptest` 执行真实 CLI，核验全通过、断言失败、网络发送失败和非法输入退出码；独立 JSON 解码核验版本、顺序、跳过项。扫描 stdout/stderr/报告，测试凭据不泄露；运行前后数据逐字节不变，无窗口、无互联网请求。

### P2：可审阅的受限 HTTP → k6 脚本导出

- **用户场景**：用户在 Reva 调通接口，再让性能同事用 k6 或 Operator 做大负载测试。
- **现有缺口**：原生 JSON 不能直接作为 k6 脚本；照搬 pm 脚本或重做压测引擎都容易产生错误语义。
- **最小 PR**：先做纯离线转换与导出审阅，第一版只接收 HTTP(S) 的 GET/HEAD、查询和请求头。用 `__ENV.BASE_URL` 等参数，变量和认证值默认外置，复用显式头优先于生成认证的规则。有正文、文件引用、前后置脚本、未支持认证/传输选项或 WS 时明确阻断，用户缩小选择后重试。只生成文件，不运行/下载 k6，不自动设置压测并发，不写入 token。
- **依赖/范围**：可独立于前两项；复用请求快照、认证解析和导入审阅交互经验，需协调集合与 i18n 文件。不复制 k6 代码，不把 k6 作为 Reva 库依赖。
- **验收**：固定集合检查重复查询、禁用行和特殊字符保真，测试敏感值不出现在脚本/说明中；脚本、WS 和不支持选项必须阻断且原数据不变。可选集成验收用预装固定版 k6 对 `httptest` 运行单 VU 单迭代，核对服务端实际请求；缺工具时不联网安装。

**适合直接集成专门工具的范围**：高并发、恒定到达率、分位数聚合、浏览器 Web Vitals、分布式压测和复杂指标输出。Reva 提供请求编辑、运行前审阅与最小可移交脚本，k6 承担性能执行；Mock、完整 schema 校验和跨浏览器兼容也不应夹带进这些 PR。
